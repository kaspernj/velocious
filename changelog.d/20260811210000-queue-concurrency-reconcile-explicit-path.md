Background-job queue-cap reconciliation no longer runs during schema/tenant checks or routine connection initialization: those paths are now read-only regarding queued `background_jobs` rows, so concurrent tenant initialization (e.g. `db:tenants:check --parallel N`) cannot deadlock against active job processes with the broad adoption/release UPDATEs. Adding, removing, or changing `queues[name].maxConcurrent` is still reconciled against the persisted backlog when the background-jobs main process starts, now serialized across processes with a database advisory lock via the explicit `BackgroundJobsStore#reconcileQueueConcurrency()` lifecycle path. See `docs/background-jobs.md`.
