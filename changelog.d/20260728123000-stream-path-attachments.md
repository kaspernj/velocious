Node `{path, filename?, contentType?}` record attachment inputs now keep one allowlisted, opened regular-file source plus its stat-derived byte size through normalization instead of materializing the whole file as a Buffer and Base64 string before storage. On current nullable schemas, filesystem persistence uses a bounded, backpressured stream and staged rename, S3 sends a Node `Readable`, and native compatibility buffering stays inside the native driver, including for preconstructed driver instances. Legacy non-null `content_base64` schemas instead materialize the opened snapshot exactly once before driver persistence and reuse the same Buffer/Base64 for backing storage and the database row. Pathname replacement cannot switch the source, truncation is rejected, later appends are ignored, and the source is always closed. Existing in-memory, UploadedFile, browser, replacement, and commit-aware cleanup behavior remains compatible.
