Promoted the process-local advisory-lock tier from the SQLite driver into the shared base driver, so every driver (MariaDB, PostgreSQL, SQL Server, SQLite) runs advisory locks as a two-tier chain (STC-211, epic STC-209).

- Acquisition now goes: **process-local pre-filter tier** (a process-wide FIFO waiter queue per lock name in `src/database/drivers/base.js`) → **driver-native tier** (`GET_LOCK` / `pg_advisory_lock` / `sp_getapplock` / the Node SQLite filesystem lock). A same-process waiter is served from the queue without issuing any driver-native lock query and without parking a pooled connection in a driver lock state — this is the connection-pinning fix the advisory-lock epic exists for.
- The tier is a **pre-filter, never the authority**: a grant means only "you are next in this process." Cross-process/cross-host exclusion is still confirmed by the driver-native tier; if it denies or times out, the in-process hold is rolled back and the next waiter is served. Plain SQLite (web/sql.js, Expo native) has no native tier, so its locks stay documented as process-local only.
- Semantics preserved: `withAdvisoryLock` / `withAdvisoryLockOrFail`, `AdvisoryLockTimeoutError` / `AdvisoryLockBusyError` / `AdvisoryLockHoldTimeoutError`, `dedicatedConnection`, `holdTimeoutMs` + `TimeoutControl`, counted re-entrant registries and `releaseHeldAdvisoryLocks()` cleanup. Re-entrancy is per driver (`supportsReentrantAdvisoryLock`): session-scoped DB locks stay re-entrant, the SQLite emulation stays contention-on-re-acquire.
- The bounded acquire timeout (`DEFAULT_ADVISORY_LOCK_ACQUIRE_TIMEOUT_MS`, 1.0.693) now covers the whole two-tier chain on every tier.
- Docs: "Scope" and driver-support table in `docs/advisory-locks.md` describe the chain; tests: `spec/database/drivers/process-local-advisory-lock-tier-spec.js` (FIFO without native queries on MariaDB/PostgreSQL/SQLite, tier-not-authority, bounded timeout, per-instance ownership).
